# T-098: Design: full-run pacing (78 min at 1x vs 30-40 min target)

Milestone: M5 | Type: design | Owner: claude | Scenario: `default`

## Goal

The owner wants pacing fixed **before v1 ships** (OWNER_REQUESTS R-4). T-028 measured a full seed-1337 sensible
win at 4731 simulated seconds: **78:51 at 1x** (about 26 min at 3x). GDD §1 promises about 30–40 minutes at 1x.
Bring the full run close to the target with **data changes**, keep win rates about the same, and record the
decision.

## Context

- 20 days × `day_length` 150 s = 3000 s (50 min). The other ~1730 s are nights (avg ~87 s, floor
  `night_min_length` 45 s, cap `night_max_length` 300 s). Nights end when the wave is dead, so their length
  depends on spawn distance, zombie speed and kill rate, not on one number.
- Arithmetic: even with very short days the nights alone are ~29 min, so 30–40 min at 1x needs both shorter days
  **and** somewhat shorter nights, or the target is restated (for example "about 45 min at 1x, under 25 at 2x").
- `game/scripts/sim/game_clock.gd` reads one `day_length`. A per-day ramp (long early days, shorter later days)
  needs code. If you choose a ramp, don't write code: make the data-only part here, and say in `work.json`
  exactly which code task the reviewer should file (key name, shape, fallback). The reviewer files it as M5,
  priority 1, `"status": "ready"`, so it sorts ahead of T-033 (priority 2) and lands before the export.
- Shorter days mean less production per day. Scale production (gather times, `food_per_farmer`, workshop
  `craft_time`, build times) so per-day output stays about the same, or the economy collapses late.
- Balance bot: `godot --headless --path game --script res://dev/balance_run.gd -- --strategy=both
  --seeds=1337,1,2,3,4 --out=<abs path under project/runs/T-098/>`. Baseline (T-027/T-028): sensible 3 won,
  1 survived, 1 lost; none loses on night 4 on all seeds. Seeds 5–9 are a useful extra check (8/10 baseline).
- `test_full_run_qa.gd` asserts full-run facts on seed 1337; several tests read `day_length`
  (test_game_clock, test_day_night, test_dawn_rules, night_sim_fixture, ...). Prefer tests that read the value from
  data; if a test pins 150 literally, update the expectation and say so.

## Do

1. Measure the current full-run length per phase (day vs night seconds) on seed 1337.
2. Pick the target full-run length at 1x and the data changes. Try only a few iterations; prefer the smallest
   set of changes that gets there.
3. Edit `game/data/*.json` only (plus test expectations that pin changed numbers).
4. Re-run the 5-seed bot and the full test suite.
5. Record the decision, numbers and old → new values in `project/decisions.md`. If the target changes, update GDD
   §1 and log that change.

## Acceptance criteria

- Decision recorded in `project/decisions.md` with the target full-run length at 1x and the measured new length
  on seed 1337 (simulated seconds and mm:ss).
- Full seed-1337 sensible run at 1x is within the target (aim ≤ 45 min), or the GDD target is restated with a
  reason.
- 5-seed balance output (seeds 1337,1,2,3,4) shows sensible ≥ 3 wins and none losing on nights 3–6 on every seed.
  BALANCE lines are in `work.json`.
- All tests pass (including `test_full_run_qa.gd`); import and smoke clean.

## Pitfalls

- Don't shorten nights by raising zombie speed so much that walls stop mattering.
- Keep `night_max_length` high enough for a final-horde night (T-093 cap, 300 s).
- The top bar shows "Nightfall in m:ss"; any day length works there.
