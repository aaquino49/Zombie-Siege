# T-078: Zombie target priorities: runners chase survivors, brutes smash structures

Milestone: M3 | Type: code | Owner: gemini | Scenario: `zombie_types`
Depends on: T-018 (done). Split out of T-020 so the wave spawner stays small.

## Goal

GDD §8: runners target survivors first, brutes target walls and buildings first. Walkers keep today's behaviour.
The type is read from `zombies.json` `"target_priority"` (`"command_center"`, `"survivors"`, `"structures"`), never
from the type id.

## Work (all in `game/scripts/sim/`)

1. `Zombie`: add `priority: String` (filled by `ZombieStore.add` from `target_priority`, default `"command_center"`).
2. `balance.json`: `"runner_seek_tiles": 6.0`.
3. `ZombieAI.tick`, before the existing survivor-in-range step:
   - **"structures" (brute):** if a building occupies one of the 4 orthogonal neighbours of the zombie's tile (or the
     tile itself) and it isn't the CC, attack it (keep the current `target_building_uid` while it lives; otherwise
     the lowest uid). This runs before survivor targeting. When nothing is adjacent, fall through to normal logic.
   - **"survivors" (runner):** find the nearest non-sheltered, not-on-tower survivor (check `on_tower` only if the
     field exists; T-019 adds it) within `runner_seek_tiles`. If found and outside attack range, step toward it: pick
     the 8-neighbour of the zombie's tile that is closest to the survivor, in bounds, `map.is_passable` and has no
     building. If that neighbour exists, move toward its centre at the zombie's speed (same movement code style as
     now, factor a `_move_toward(z, target_pos, dt)` helper rather than copy-pasting it a fourth time). If no such
     neighbour exists (wall in the way), use the flow field as today. In attack range, the existing survivor attack
     applies.
   - Remove the leftover `# Wait, what if b_target == null...` comment if T-073 hasn't already.
4. Keep `zombie_ai.gd` under ~400 lines; split helpers into `zombie_targeting.gd` if needed.

## Scenario `game/dev/scenarios/zombie_types.gd`

Daytime, `Game.state.waves.enabled = false` if `waves` exists. A wall line east of the CC with a gap. A gatherer
working a node ~5 tiles outside the wall; a runner spawned 8 tiles from it; a brute next to the wall line; a walker.
Tick ~3 s, pause: the runner has turned toward the gatherer, the brute is hitting a wall (damaged HP bar), the walker
heads for the gap. Camera framing all three.

## Tests: new `game/tests/test_zombie_priorities.gd`

- A runner 4 tiles from an exposed survivor moves closer to that survivor (not along the flow field) within 1 s.
- A runner whose straight step toward the survivor is blocked by a wall follows the flow field instead.
- A runner ignores sheltered survivors and survivors beyond `runner_seek_tiles`.
- A brute adjacent to a wall attacks the wall even when a survivor is within 1.5 tiles; a walker in the same spot
  attacks the survivor.
- A brute next to the CC with no other building adjacent still attacks via the existing logic (the CC is the goal).
- `priority` comes from data: changing `target_priority` in a test GameData copy changes behaviour.
- Existing `test_zombies.gd` / `test_flow_field.gd` pass unchanged (walkers unchanged), including the 250-walker
  performance test.

## Acceptance criteria

- New tests pass; all tests pass with no SCRIPT ERROR; import/smoke clean.
- `zombie_types` screenshot shows the three behaviours; `zombies` and `zombies_perf` screenshots unchanged.
- No type-id string checks (`type_id == "runner"`) in AI code.

## Pitfalls

- Runner seek is O(zombies × survivors); fine at 30 survivors, but skip it for non-runners.
- Don't let a runner step diagonally between two solid tiles (corner cutting through a wall seam): require both
  orthogonal neighbours of a diagonal step to be passable.
