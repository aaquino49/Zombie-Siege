## Targets (5 seeds: 1337, 1, 2, 3, 4)

1. `sensible` survives all 20 nights with the radio tower complete (`won`) on at least 4 of 5 seeds. Median
   final CC HP above 30%.
2. Pressure: `cc_min_hp_pct` drops below 80% on some night from 15 to 20 on at least 3 seeds. Nights 1–5 should
   rarely touch the CC.
3. `none` loses on nights 3–6 on every seed. Don't make the do-nothing player lose on night 1.
4. Economy feels busy: `sensible` dusk ammo isn't stuck above 300 for the whole mid-game, and the radio tower gets
   placed by about day 10–12.

## Levers, in order of preference

1. **Starting state** (`balance.json`): `start_jobs`, `start_ammo`, `start_wood`, `start_scrap`.
2. **Ammo economy:** workshop `ammo_per_scrap` / `craft_time`, `guard_damage`, `guard_fire_interval`, turret
   `damage` / `fire_interval`. Since one crafter is the bot's ceiling, faster crafting moves the cliff further
   than a bigger stock does.
3. **Wave curve** (`waves.json`): `walkers_base`, `walkers_per_night`, the runner/brute offsets, `final_multiplier`.
   Flattening late growth a little turns the cliff into a slope.
4. **Zombie stats** (`zombies.json`): walker damage and HP. Last resort, because these numbers are in the GDD tables.
5. Costs/HP in `buildings.json` only if a building is clearly never worth it.

## Method

- Reuse attempt 1's runner `project/runs/T-027/attempt1_data/run.sh <name>` (one process per seed, prints the outcome lines
  and a per-night `night:cc/dusk_ammo/guards` strip). Copy it to `project/runs/T-027/pass2/run.sh` first and point
  `OUT` and the log paths at `pass2` (new attempts reuse the `a1`–`a3` folders). Change one or two levers per iteration.
- **Budget: at most 8 iterations.** After every iteration, append one line to
  `project/runs/T-027/iterations.md` (iteration → change → BALANCE_SUMMARY lines → one-sentence read). That file
  survives a revert, so a later attempt can pick up where you stopped.
- **Write `work.json` early.** As soon as one iteration meets targets 1 and 3, run the test suite, update the
  docs and write `work.json`. Only then try further iterations for targets 2 and 4, updating the docs and
  `work.json` again if a later one is better. A limit cut must never cost the whole task again.
- After the final data change, run the full test suite (`godot --headless --path game --script res://tests/run_tests.gd`).
  If a test pins a changed data value as a literal, prefer a lever that no test pins. If a pinned value really must
  change, update only that literal expectation and list it in `work.json`. No other code changes.

## Acceptance criteria

- Targets 1–4 met, or every miss is explained in `decisions.md` with the reason it was accepted.
- Only `game/data/*.json`, `project/GDD.md`, `project/decisions.md`, `project/assumptions.md` and (only if
  unavoidable) literal expectations in `game/tests/` changed (plus files under `project/runs/T-027/`).
- Full test suite passes. Import and the 300-frame smoke run are clean.

## Pitfalls

- **If the bot is the limit, not the game, stop tuning that axis.** For example, if it never uses a second
  crafter, never builds a second farm in time, or starves with idle gatherers, say so in `work.json` `summary`
  with the evidence (CSV columns, nights), so the REVIEW step files a small bot-fix task. Don't edit
  `balance_bot.gd` yourself, and don't over-tune the data to cover for a weak bot.
- If a target can't be reached with data alone (a mechanic is missing), record it the same way.
- The bot is a proxy for a human. A human pauses, reacts and re-assigns guards, so leave a small margin of safety
  rather than tuning the bot exactly to the edge.
- Nights now end after at most 300 s (T-093), and any remaining zombies retreat. If many nights hit that cap
  (survived nights with zombies left over), that's a sign the defense can't finish waves. Note it.
