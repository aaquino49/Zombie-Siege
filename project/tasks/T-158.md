# T-158: Cleanup: save/continue hardening follow-ups from T-146

Milestone: M7 (starts after the v1.1.0 export T-114) | Type: code | Owner: codex | Scenario: `main_menu_continue` | skip QA

## Goal

Four small fixes found in T-146's review. Files: `game/scripts/autoload/game.gd`, `game/scripts/ui/main_menu.gd`
(and their tests). Keep every public `Game` API and button node path unchanged.

## Do

1. **No crash on a vanished save.** In `Game.new_game()`, if `SaveGame.restore(...)` returns null for
   `_pending_continue` (file changed between the menu check and the transition), `push_warning`, delete the save and
   fall back to `GameState.new(data, map_seed)`. Today it crashes on `state.clock`.
2. **Dead guard.** In `save_now()`, the `_is_automated_run() and target_path == SAVE_PATH` guard can never be true,
   because `_path_or_default` already redirected the path. Remove it (or keep it with a comment that says why).
3. **Stale automated saves.** Automated runs leave `user://automated_save_<pid>.json` behind when they reach a dawn.
   Delete the current process's slot on `Game._exit_tree` / `NOTIFICATION_WM_CLOSE_REQUEST`, or remove stale
   `automated_save_*.json` at startup of an automated run.
4. **Parse once.** `MainMenu._refresh_continue` calls `has_save()` and `save_day()` back to back; each parses the file
   and runs `SaveGame.restore` with `GameData.load_default()`. Read once and reuse the result.

## Acceptance criteria

- A save that becomes invalid between `has_save()` and `continue_game()` starts a fresh game with a warning (unit test).
- After a headless run that reaches dawn, no `automated_save_<pid>.json` for that process is left in `user://`.
- Opening the main menu parses the save at most once (unit test with a counter or spy).
- All tests, import, smoke, `qa_m4_menu_flow.gd` and the `main_menu_continue` capture clean.

## Pitfalls

- Never touch the player's real `user://savegame.json` from tests; use the disposable-path helper T-146 added.
- Don't edit `save_game.gd` (T-155 and T-147 own it).
